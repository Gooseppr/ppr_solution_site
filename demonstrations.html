Une source Odoo réelle

Le fichier account_data.xml provient du module account d’Odoo 19. Il contient des objets de configuration : délais de paiement, méthodes de paiement, actions et autres paramètres.

account_data.xml · délai de paiement à 30 joursExtrait réel
  1. <record id="account_payment_term_30days" model="account.payment.term">
  2. <field name="name">30 Days</field>
  3. <field name="note">Payment terms: 30 Days</field>
  4. <field name="line_ids" eval="[Command.clear(), Command.create({'value': 'percent', 'value_amount': 100.0, 'nb_days': 30})]"/>
  5. </record>

Extrait du délai de paiement à 30 jours. Le corpus contient de la configuration logicielle, sans données comptables de clients.

Consulter la source Odoo et sa version exacte →

Du balisage à la donnée exploitable

  1. Lire les enregistrements. Repérer les objets record, leurs identifiants et leurs modèles.
  2. Extraire les champs et les références. Conserver les expressions de configuration sous forme de texte, sans les exécuter.
  3. Contrôler le résultat. Vérifier les 21 enregistrements et comparer la transformation JSON à son résultat attendu.
  4. Préparer les livrables. Exporter les données extraites dans un classeur et un CSV pour consultation et filtrage.

Le même travail peut servir à un inventaire, une analyse de configuration ou la préparation d’une migration. Le chargement fonctionnel dans Odoo reste un contrôle distinct.

Un objet prêt à être repris

Le délai de paiement à 30 jours devient un objet JSON. Son identifiant et son modèle sont conservés ; la commande de configuration reste une chaîne de caractères.

Le même contenu, du balisage à la page

Cette procédure de démontage et remontage d’un pneumatique provient du corpus officiel S1000D Bike. Les aperçus ci-dessous sont tirés du XML source et du PDF réellement produit par PPR.

Une véritable procédure S1000D

Le module 921A décrit une opération de maintenance du vélo. Le document source distingue l’identité du module, les références, les exigences préliminaires et les étapes opératoires.

Bike · les quatre premières étapesExtrait réel
  1. <mainProcedure>
  2. <proceduralStep>
  3. <para>Lift and turn the bicycle and make sure the bicycle is held safely in this position.</para>
  4. </proceduralStep>
  5. <proceduralStep>
  6. <para>Use a standard wrench from the <internalRef internalRefId="seq-0001" internalRefTargetType="irtt05"/> and loosen the brake caliper.</para>
  7. </proceduralStep>
  8. <proceduralStep>
  9. <para>Remove the axle bolt.</para>
  10. </proceduralStep>
  11. <proceduralStep>
  12. <para>Remove the wheel.</para>
  13. </proceduralStep>
  14. </mainProcedure>

Extrait des quatre premiers proceduralStep ; l’indentation est adaptée à la lecture. Le module complet est transformé pour produire le PDF.

Provenance : S1000D Issue 6, Bike Sample Data Set →

Adapter la publication par le profil XSLT

Le moteur transforme le XML en XSL-FO avec Saxon, puis compose le PDF avec Apache FOP. Deux profils de procédure produisent deux rendus du même module. La source métier reste identique.

S1000D est ici un exemple concret de notre spécialisation documentaire. Le principe de publication par XSLT s’applique aussi à d’autres structures XML, avec un profil adapté au modèle source et aux exigences de présentation.

Ce qui a été vérifié sur le PDF

  • Transformation Saxon et génération XSL-FO réussies.
  • PDF v3 de 6 pages, texte extractible, aucune page vide détectée.
  • Cinq signets, aucun signet non résolu.
  • Identité du module, références, exigences préliminaires, procédure et fin de module présentes.
  • Aucun avertissement ni erreur FOP sur ce rendu.

Le rapport de contrôle XML contextuel signale encore un écart de cardinalité et trois constats de choix sur ce module officiel. Le PDF est généré ; cette démonstration ne vaut pas certification de conformité S1000D. Les constats restent consultables dans la fiche de provenance.
